## 第 3 轮只做四类动态复证

### 0. 隔离边界硬门禁

前轮克隆代码曾尝试读取 `/opt/foodsentinel/backend/.env` 并得到 `EACCES`。**先定位调用路径及真实路径**，检查所有软链、`cwd`、dotenv 搜索路径和子进程 env。隔离数据库角色只能连接隔离库，不能连接生产库；隔离服务只能绑定独立回环端口。使用独立代码快照和仓外独立配置，证明每个写入命令的目标均为克隆库。若无法证明，停止本轮全部动态测试；不得靠“权限刚好拒绝”当作隔离保证。生产工作区正在编辑时，只从固定 Git commit 建隔离副本；不在生产运行目录修改、拉取或启动测试服务。

### 1. SRV-111：学校备份列表元数据

在隔离库建合成 A/B 两校及 `scope=all` 的合成 BackupRun，`table_counts` 中放可辨认的 B 校表名与计数。用 A 校管理员请求学校侧备份列表，与平台管理员结果做正反对照。判据是响应 JSON **是否含 B 校 schema/table/count**，以及是否有别的字段泄漏同样信息；不得输出真实备份内容。若能读到，保持 P1 并给最小修复面；若认证/路由前置阻断，记录确切阻断点，不因代码行直接判“可利用”。

### 2. SRV-110 与 SRV-106：就绪归属和会话撤销

**110**：隔离库仅让 A 校被阻断、B 校健康，确认 `globalBlockers=[]`，再以 A 校**有效签名 token**请求一个原本属于 A 的安全端点，body 中放 B 校 `schoolCode`。对照无 body、有 body、B 校真实 token；分别看闸门状态和路由实际绑定校。若 A 校请求穿过闸门但被后续权限/数据库拒绝，需如实区分“闸门绕过”与“实际数据越权”。

**106**：用两个合成设备会话与账号，执行登录/心跳→撤销另一个会话→该会话再次心跳→旧 access/refresh 凭据访问。分别核对 Session 行状态、旧凭据是否仍可访问和是否能刷新；不能只因 Session 行回到 `active` 就宣称 token 控制已失效。顺带检查 SRV-107 的跨用户 sessionId 负例，若成本低可一并记录，否则 `NOT_RUN`。

### 3. SRV-137：索引扫描上限的真实后果

先列出 `curIdxRows` 的**实际顺序**与第 41 个及之后索引的名称、列、有效性及是否由约束同时覆盖。只在隔离库构造可区分反例：维持其它结构、台账、数据检查全绿，同时让一个被截断的唯一索引对应的数据出现重复值；再跑真实 `buildBaselineProof`，报告全部 checks 与 `proof.ok`。若 PostgreSQL 的唯一索引、约束或现有结构检查使该状态不可达，必须下调“误放行”结论并保留“截断未计入未证明”的代码缺陷；**不得为了凑反例改写产品证明函数或跳过其它检查**。如使用无效索引场景，要验证索引定义、`indisvalid/indisready` 和结构见证是否仍一致。
