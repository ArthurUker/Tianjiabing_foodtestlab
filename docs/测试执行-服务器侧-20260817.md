### VS Code 连接服务器（Remote-SSH）

1. VS Code 安装扩展 **Remote - SSH**。
2. 添加 SSH 配置（`.ssh/config`，把 `<用户>` 换成实际登录账号，常见为 `root` 或部署用户 `foodtestlab`）：

   ```ssh-config
   Host foodtestlab
       HostName 111.231.166.161
       User <用户>
   ```

3. 命令面板（`Ctrl+Shift+P`）→「Remote-SSH: Connect to Host」→ 选 `foodtestlab`。
4. 连接成功后通过「文件 → 打开文件夹 → `/opt/foodtestlab`」打开项目，在**集成终端**里执行下文命令。

> ⚠️ 注意：以下命令均在 **Linux 服务器终端**执行。Windows PowerShell 的 `sudo` 不支持 `-u` 参数，
> 切勿在本地 PowerShell 里跑 `sudo -u postgres` 类命令（会报 `error: unexpected argument '-u'`）。
> 用 VS Code Remote-SSH 连上 Linux 服务器后执行即可。

## 一、B7-旧schema：旧 schema 保留与清理（SSH psql）

> **目标**：影子恢复（RESTORE）后会保留 `school_xxx_old_<时间戳>` 旧 schema，确认其存在且不影响正式数据，必要时清理。

### 执行步骤

1. 连接服务器（VS Code Remote-SSH），确认后端服务正常：

   ```bash
   systemctl status foodtestlab-api --no-pager | head -20
   curl -s http://127.0.0.1:3000/api/health
   ```

2. 查看是否存在影子恢复产生的旧 schema（关键命令）：

   ```bash
   sudo -u postgres psql -d foodtestlab -c "SELECT nspname FROM pg_namespace WHERE nspname LIKE 'school_%_old_%' OR nspname LIKE 'school_%_restore';"
   ```

   或交互式查看全部 schema：

   ```bash
   sudo -u postgres psql -d foodtestlab -c '\dn'
   ```

3. 若查到 `school_<code>_old_<时间戳>` 形式的旧 schema：
   - 先确认不影响正式数据（正式 schema 名为 `school_<code>`，无 `_old_`/`_restore` 后缀）。
   - 如需清理（将 `<schema名>` 换成实际查到的名字）：

   ```bash
   sudo -u postgres psql -d foodtestlab -c 'DROP SCHEMA "school_dmyz_old_20260812xxxxxx" CASCADE;'
   ```

4. 清理后再查一次，确认已消失：

   ```bash
   sudo -u postgres psql -d foodtestlab -c "SELECT nspname FROM pg_namespace WHERE nspname LIKE 'school_%_old_%';"
   ```

### 判定

- ✅ **通过**：旧 schema 存在且不影响正式数据；或已用 `DROP SCHEMA ... CASCADE` 清理成功。
- ❌ **失败**：DROP 报错、或清理后正式 schema 数据丢失/服务异常。

## 二、B8：维护模式写阻断（READONLY_MODE）

> **目标**：开启维护模式（`READONLY_MODE=true`）后，读操作（打开登录页）正常，写操作（新增检测记录）被阻断返回 503；验证后恢复正常。

### 执行步骤

1. 备份当前 `.env`（可回滚）：

   ```bash
   cp /opt/foodtestlab/backend/.env /opt/foodtestlab/backend/.env.bak-$(date +%F)
   ```

2. 在 `/opt/foodtestlab/backend/.env` 末尾追加维护模式开关：

   ```bash
   echo 'READONLY_MODE=true' >> /opt/foodtestlab/backend/.env
   ```

3. 重启后端服务使配置生效：

   ```bash
   sudo systemctl restart foodtestlab-api
   systemctl status foodtestlab-api --no-pager | head -20
   ```

4. **读操作验证**（浏览器）：打开 `http://111.231.166.161:8080/tjb/login.html`，应能正常打开登录页。

5. **写操作验证**（浏览器）：用 tjb 学校管理员登录 → 进入任一检测栏目（如果蔬农残）→ 新增一条记录点「保存」。
   - 预期：保存被阻断，提示「系统维护中 / 维护模式」或类似，请求返回 503。

6. **恢复正常**：

   ```bash
   sed -i '/^READONLY_MODE=true$/d' /opt/foodtestlab/backend/.env
   sudo systemctl restart foodtestlab-api
   curl -s http://127.0.0.1:3000/api/health
   ```

7. 浏览器硬刷新后再次登录，确认新增记录恢复正常。

### 判定

- ✅ **通过**：维护模式下登录页可打开、新增记录被阻断（503/维护提示）；恢复后写操作正常。
- ❌ **失败**：维护期间仍能写、或读操作也异常、或恢复后服务异常。

## 三、B9：SSH 侧检查（定时任务 / 文件权限 / 失败告警）

> **目标**：服务器侧备份定时任务、备份文件权限、失败告警机制均正常（FIX-07 已修复）。

### 执行步骤

1. **备份定时任务**（应显示 `foodtestlab-api-backup.timer` 为 active）：

   ```bash
   systemctl list-timers --no-pager | grep -i backup
   systemctl status foodtestlab-api-backup.timer --no-pager | head -15
   systemctl status foodtestlab-api-backup.service --no-pager | head -15   # 最近一次执行状态
   ```

2. **最近一次备份执行日志**（确认 02:00 定时任务真正跑过且无错误）：

   ```bash
   journalctl -u foodtestlab-api-backup.service -n 30 --no-pager
   tail -30 /mnt/datadisk0/foodtestlab/logs/backup.out.log
   ```

3. **备份文件权限**（`.aes` 密文与 `.meta.json` 应 600、日期目录 700、根目录属主 `foodtestlab`）：

   ```bash
   ls -la /var/backups/foodtestlab/
   ls -la /var/backups/foodtestlab/$(date +%F)/   # 最近备份日期目录
   find /var/backups/foodtestlab -name '*.aes' -o -name '*.meta.json' | head -10 | xargs -r ls -la
   ```

4. **失败告警钩子**（OnFailure 配置存在、告警脚本可执行、告警日志可写）：

   ```bash
   systemctl cat foodtestlab-api-backup.service --no-pager | grep -A2 OnFailure
   ls -l /opt/foodtestlab/scripts/backup-alert.sh
   tail -5 /mnt/datadisk0/foodtestlab/logs/backup.err.log 2>/dev/null || echo '(暂无告警日志，正常)'
   ```

5. **手动触发一次备份做完整性验证（可选，推荐）**：

   ```bash
   cd /opt/foodtestlab/backend && sudo -u foodtestlab /usr/local/bin/node scripts/003_backup-now.mjs --all --dry-run
   ```

   > 确认加密模式（腾讯云 KMS 或 `BACKUP_MASTER_KEY`）已配置；`dry-run` 只打印计划不执行。
   > 如需真实执行一次去掉 `--dry-run`（产生一份新备份，不影响现有数据）。

### 判定

- ✅ **通过**：`foodtestlab-api-backup.timer` active；最近备份有产物；`.aes`/`.meta.json` 权限 600、目录 700；
  `backup-alert.sh` 存在且 OnFailure 已挂接。
- ❌ **失败**：timer 未激活 / 无备份产物 / 权限过宽（644 等）/ 告警钩子缺失 / 备份日志有错误。
