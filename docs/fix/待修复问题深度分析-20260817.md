### 2.1 权限与会话边界（P0 最高优先级）

#### 2.1.1 P10 / P11 —— 用户角色变更/禁用后，旧会话未失效，前端收到 401 不登出

- **实际表现（汇总报告）**
  - P10："用户被禁用/改角色后，已登录会话仍可访问数据"
  - P11："禁用用户后，该用户仍保持登录状态并可操作"
- **截图证据**
  - P10 图 1：用户 `456 / 操作人员` 正常进入数据看板。
  - P10 图 2：右侧 DevTools 满屏 `401 Unauthorized`，所有模块 `Sync failed: Fetch failed: 401 Unauthorized`。
  - P11 图 1：在管理后台编辑用户 `456`，角色仍为"操作人员"。
  - P11 图 2：回到数据看板，仍显示 `456 / 操作人员`，DevTools 仍报 401。
  - P11 图 3：用户 `456` 在登录页输入密码后提示"登录失败 401"。
- **根因分析**
  1. **后端**：修改/禁用用户后未使该用户已有 token/refresh token 失效；或 `/api/me`、`/api/*` 在 401 时未触发前端登出。
  2. **前端**：`StorageService._syncFromApi` 捕获 401 后只做控制台报错，未调用 `logout()` 或 `redirectToLogin()`。
- **修复建议**
  - 后端：用户状态/角色/密码变更时，把该用户所有活跃 token 加入黑名单或缩短 token 有效期，强制重新登录。
  - 前端：统一在 axios/fetch 拦截器里处理 401，清掉 localStorage 中的 token 并重定向到登录页。

### 2.5 测试报告汇总生成链路的缺陷（重要新增）

除了业务 bug，"测试报告汇总"本身也存在多个影响分析准确性的问题，需一并修复：

#### 2.5.1 证据图片 URL 拼接错误导致截图丢失（P06 / B9）

- **现象**：P06、B9 的 `evidence` 字段里，多个 URL 被拼接成单个字符串：
  ```text
  /api/test-results/evidence/P06/1786693991312_1b0d8563.png/api/test-results/evidence/P06/1786694000349_c5ea949d.png
  ```
  导致 `testReportSync.js` 的 `tokenizeEvidence` 无法识别，`docs/test-results/latest/evidence/P06/`、`B9/` 目录缺失。
- **影响**：汇总报告中 P06、B9 没有证据图，分析人员无法复现现场。
- **修复建议**：
  - 前端上传证据时确保 `urls` 数组每个元素只含一个 URL；
  - 后端 `parseEvidenceList` 增加兜底：对单个字符串再做一次拆分，兼容这种脏数据。

#### 2.5.2 `fixNote` 静态标记与实测结果冲突

- **现象**：`backend/lib/testCaseDefs.js` 的 `FIXED_CASE_NOTES` 给 R01/R03/R06/R07/R13/R15/R19/B7/B9/V1-果蔬 等打了"已修复"徽章，但当前实测仍 `failed` 且未 `closed`。
- **影响**：汇总报告同时显示"🔧 已修复"和"❌ 失败"，误导负责人以为"已修复待复测"，实际可能是根本没修复。
- **修复建议**：
  - 要么把 `fixNote` 改名为"修复中/待复测"，避免"已修复"这种结论性词汇；
  - 要么增加规则：当 `result === 'failed'` 时不显示"已修复"徽章，避免自相矛盾。

#### 2.5.3 B7 无证据图

- **现象**：B7-旧 schema 用例在汇总报告中无证据；0814 文档提到 B7 是 SSH/psql 手动验证项。
- **影响**：无法判断 B7 失败是代码问题还是测试环境/操作问题。
- **修复建议**：要求测试人员补传 B7 的 psql 查询结果截图或脚本输出。
