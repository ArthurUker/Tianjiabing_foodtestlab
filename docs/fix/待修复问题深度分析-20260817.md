- **实际表现（汇总报告）**

  - **P10** `detail`："把操作者修改成查看者之后，刷新页面账户类别没更改成查看者，刷新2次页面之后就需要重新登录，重新登录就改成查看者"
  - **P11** `case_title`："禁用用户后会话立即失效"
  - **P11** `detail`："禁用用户后，该用户仍保持登录状态，刷新页面之后报错，但是账户没有退出"
- **截图证据**
  - P10：用户 `456 / 操作人员` 进入数据看板；管理后台将其改为查看者后，数据看板仍显示 `456 / 操作人员`。
  - P11：禁用 `456` 后，数据看板 DevTools 满屏 `401 Unauthorized`，但页面未自动跳转到登录页；登录页输入密码提示"登录失败 401"。
- **代码级分析（authMiddleware.js）**
  - 后端 `authMiddleware.js:358-360` **每次请求都用 DB 当前角色覆盖 token 角色**：
    ```js
    if (dbUser.role && VALID_ROLES.has(dbUser.role) && dbUser.role !== u.role) {
      u.role = dbUser.role
    }
    ```
  - 后端 `authMiddleware.js:340` 已检测 `dbUser.status !== 'active'` 返回 401。
  - **结论**：后端能力已实现；P10/P11 失败完全在**前端**：
    - **P10** = 前端 UI 显示的角色来自 `localStorage` 缓存的 `current_user`，未随后端角色覆盖而更新；需二次刷新才触发重新登录，重登录后才显示正确。
    - **P11** = 前端收到 401 后未强制跳转登录页，`StorageService._syncFromApi` 仅控制台报错。
- **修复建议**
  - 前端统一拦截 401 → 清 token + `redirectToLogin()`。
  - 前端每次进入应用/切换学校时从 `/api/user/me` 拉取最新角色写入 UI，不要依赖 localStorage 旧角色。

- **截图证据**
  - R08："整改与复检管理"弹窗"复检结果已保存"，右侧"已录入的复检记录"显示"暂无复检记录"。

  - **对照项 Q1-果蔬阶段A = passed**（"复检合格没有出现问题"）：证明复检 bug **只在"保存后刷新列表/页面"时触发**。
- **代码级根因（已回溯）**
  1. 后端 `recordNormalize.js` 的 `buildRecordWriteData` 把 `recheckRecords/recheckReports` 写入 `result_data`（jsonb），`buildRecordPayload` 读取时也返回——**后端持久化本身正确**。
  2. 后端 `recordRoutes.js` 的 `PUT /api/records/:tableName/:id` 有 `TD-Q1-Recheck-SelfHeal`，用最新复检结论覆盖 `result_data.result`，但**未同步顶层 `status`**——列表按 `status` 过滤时可能遗漏。
  3. **前端核心 bug**：`Storage.js` 的 `_handleUpdate` 在 PUT 成功后调用 `_applyServerRecord(patched)`，用**服务端返回的整条记录覆盖 localStorage 缓存**。若服务端响应中 `recheckRecords` 经 `sanitizeObjectKeys`/缓存迁移被净化，本地缓存即被清空 → 弹窗"暂无复检记录"；刷新后重新拉取时若 `status` 不一致还可能触发 400/记录不存在。
  4. `GenericTest.js:547` 保存复检时 `record.recheckRecords.unshift(newRecheck)` 后 `storage.update(record.id, record)`，依赖上述覆盖逻辑，缺"保存后显式回读校验"。
  5. **第五轮新增（S2：保存点位时清空复检）**：`Tableware.js:784-788` 在"保存 ATP 检测点位"时执行 `data.recheckRecords = []` 后 `storage.save(data)`。**关键点**：后端 `recordRoutes.js:416` 的 `tableware` 受保护字段为 `['atpPoints','sampleInfo']`，**`recheckRecords` 不在其中**，所以后端会接受并持久化这次清空。→ 任何"重新保存点位"操作都会丢失该记录的复检历史（与 R08/R28 的"复检丢失"高度吻合，可能是更直接的触发路径）。
  6. **第五轮新增（S3：复检显示双轨制）**：`Tableware.js:913-916` 显示标签用 `record.finalStatus`（'整改后复检合格' / '复检不合格'），该字段由 `Tableware.js:392/395` 在前端维护；而 `GenericTest.js:1317` 显示用 `isRecheckPassed ? '复检合格' : result`（依赖 `result_data.result`）。后端 `TD-Q1-Recheck-SelfHeal` 只更新 `result_data.result`，**不更新 `finalStatus`**。→ 同一记录在两个模块显示口径不同，且后端自愈只修一边，跨模块出现"果蔬显示合格、餐具显示不合格"的矛盾。
  7. **GenericTest 的"防幻觉"修复不彻底**：`GenericTest.js:558-561` 注释声明"不再依赖闭包 record，统一从 storage 重新拉取"，但 `this.storage.getAll().find(...)` 仍是本地缓存，若 `_applyServerRecord` 已用服务端响应覆盖缓存，拉到的仍是被净化的 `recheckRecords`——未解决根因。
- **关键判断**
  - 复检持久化问题至少影响**果蔬、食用油**；NEW-140845 还显示**肉蛋**异常，与 R08 detail "肉蛋、油正常"存在复现不一致，需复核。
  - 根因至少有 **3 条独立路径**：(a) `_applyServerRecord` 缓存覆盖；(b) `Tableware.js:786` 保存点位清空；(c) 双轨制显示口径不一致。任一条都可能单独导致复检显示/丢失异常。
- **修复建议**
  1. 前端 `_handleUpdate` 合并服务端响应时**保留本地 `recheckRecords`**，或保存复检后强制回读最新版本。
  2. 后端 `TD-Q1-Recheck-SelfHeal` 同步更新顶层 `status` **与** `finalStatus`（若为 tableware）。
  3. **`Tableware.js:786` 删除 `data.recheckRecords = []`**（或改为"仅在确实无复检时初始化"），并把 `recheckRecords` 加入 `tableware` 的 `PROTECTED_FIELDS` 避免后端误清空。

## 五、后续修复计划（方案分析）

> **本章仅做修复方案分析，不落地代码。** 每项给出：定位（代码点）、修复方案要点、验证手段。优先级沿用第三章 P0/P1/P2。

### 5.1 P0 — 必须立即修复

#### 5.1.1 复检持久化（R08 / R28 / NEW-140219 / NEW-140845）
- **方案要点（优先级：S2b 主因 → S2a 次因 → S3 口径）**
  1. **保存点位清空复检（S2b，主因）**：删除 `Tableware.js:784-788` 的 `data.recheckRecords = []`（保留 `atpPoints`/`modificationLogs` 赋值），改为仅在 `!Array.isArray(data.recheckRecords)` 时初始化为 `[]`。**同时**把 `recheckRecords` 加入 `backend/routes/recordRoutes.js:416` 的 `tableware` `PROTECTED_FIELDS`——经核实，`Tableware` 保存点位走的是已存在记录的 `update`（PUT），命中后端 `PROTECTED_FIELDS` 守卫（`incoming` 为空时用 `existing` 兜底），可有效挡住清空。注：此守卫**只对 update 生效**，create 路径不过守卫，需同步确保清空逻辑已从前端移除（双保险）。
  2. **前端缓存覆盖（S2a，次因/防范）**：在 `Storage.js` `_handleUpdate`（:447-450）合并服务端响应时，若 `incoming.recheckRecords` 为空而本地缓存非空，保留本地 `recheckRecords`；或保存复检后强制 `storage.getAllFresh()` 回读再渲染，避免弹窗"暂无复检记录"。
  3. **复检显示口径（S3，保同步非弃用）**：`Tableware.js` 的 `finalStatus`（`Tableware.js:392/395` 前端写入、`:913-916` 显示依赖）与 `recheckRecords[0].isPassed` 同源，不宜直接弃用。改为：**复检保存时同步写 `finalStatus` 与 `recheckRecords`**；后端 `TD-Q1-Recheck-SelfHeal` 自愈时同步更新顶层 `status` 与（tableware）`finalStatus`。**不可直接删 `finalStatus` 字段**，否则 `:913` 显示会出 undefined，且已有历史记录缺该字段会列表空白——若确需统一派生，须先给历史数据回填 `finalStatus`。
- **验证**：保存复检 → F5 刷新 → 列表/弹窗仍显示合格；保存点位 → 复检记录不丢失；果蔬/食用油/肉蛋跨品类回归；历史记录 `finalStatus` 非空。

#### 5.1.2 前端 viewer RBAC 控制层缺失（S1，系统性）
- **方案要点**
  1. **先定义权限数据契约（关键前置）**：经核实，前端 `js/` 全量搜索 `canWrite|hasWritePermission|isViewer|role==='viewer'` **0 处匹配**，后端 `authMiddleware.js:358` 也只塞了 `role` 单值字符串——**前后端均无权限位数据来源**。因此第一步不是"加函数"，而是定义契约：后端在登录态/用户上下文返回细粒度权限（至少区分 `canWrite` 增删改复检 与 `canExport` 导出 PDF），前端存为全局权限对象。
  2. 新增 `js/core/AuthService.canWrite()` / `canExport()` 网关，基于上述权限对象判断，**而非单 `role==='viewer'` 二值**。避免过度限制：viewer 可能允许"查看/导出"但禁"写"，P06 的"viewer 无导出"应单独由 `canExport` 控制，不被 `canWrite` 误伤。
  3. 在检测模块（果蔬/肉蛋/油/餐具/病原体）渲染时，对"保存/新增/删除/复检"按钮用 `canWrite()` 做 `hidden`/`disabled`；"导出 PDF"用 `canExport()` 控制。后端保留 403 兜底。
  4. 与 §5.1.3 配合：进入应用时刷新权限对象（见 §5.1.3 角色来源说明）。
- **验证**：viewer 账号登录各模块，"添加/保存/删除/复检"按钮不可见或置灰；导出按钮按 `canExport` 独立控制；后端仍保留 403 兜底。

#### 5.1.3 P10 / P11 会话与角色前端同步
- **方案要点**
  1. 统一 401 拦截器：前端收到 401 → 清 token + `redirectToLogin()`，不残留已禁用会话（后端 `authMiddleware.js:340-342` 已对禁用/不存在用户返回 401，前端只需消费）。
  2. **角色来源澄清（多租户）**：经核实，`authMiddleware.js:358` 覆盖的是**当前 token 绑定学校的 DB 角色**（`schoolCode` 交叉校验在 :344），即"学校内角色"而非平台角色。因此前端刷新应使用**学校内用户上下文接口**（如 `/api/schools/:code/users/me` 或登录态返回的学校内 role），**不能只拉平台 `/api/user/me`**——否则跨校不同角色场景下判断错误。进入应用/切换学校时拉取该学校内角色写入 UI，不再依赖 localStorage 旧 `current_user`。
  3. 与 §5.1.2 权限对象刷新合并进行。
- **验证**：改学校内角色为查看者 → 重进该学校即生效；禁用用户 → 任意请求 401 即跳登录页；跨校角色不一致时各自正确。

#### 5.1.4 R01 / R15 学校回收站恢复 jsonb cast 错误
- **方案要点（前提已修正）**：经回溯 `schoolRoutes.js:469-523`，**恢复路径已用 Prisma Model API**（`schoolCustomization.create`，:514）且对 jsonb 字段做了 `safeParseJson` 还原（:511-512），**不再用 `$executeRawUnsafe` 拼 `visible_types`**。因此原"改成 Prisma API"的指令打错了对象。真正 42804 的可能来源需先定位：
  1. **先 grep/复现定位**：在 `restore` 路由内打印或捕获 `customization[c]` 实际类型——若快照里某 jsonb 字段是"合法 JSON 字符串但解析后仍是字符串"（如 `visible_types` 存成了 `"\"[\\\"a\\\"]\""` 双重编码），`safeParseJson` 返回字符串而非数组，Prisma 接收字符串写 jsonb 仍报 42804。
  2. **修复**：在 `safeParseJson` 之外增加"解析结果若仍是字符串且看似 JSON 则再解析一次"的循环还原；或在 `schoolCustomization.create` 前对每个 jsonb 列做 `typeof=== 'string' ? JSON.parse : val` 二次兜底。
  3. 若 42804 实际来自 `school.create`（:494-503）而非 customization，则另查该校行 jsonb 列。
- **验证**：回收站恢复学校 → 不再报 `42804`；恢复后学校在列表可见；双重编码的脏快照能正确恢复。

#### 5.1.5 NEW-170443 平台超管修改学校用户类别 500
