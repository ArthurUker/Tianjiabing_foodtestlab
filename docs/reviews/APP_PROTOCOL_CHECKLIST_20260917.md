# App 协议核对清单（离线同步 / 并发语义）— 需 App 团队提供脱敏信息

> 用途：确认 App 与平台 `/api/sync/*`、`/api/records/*` 的契约一致。**平台不按角色决定是否启用并发控制**，
> 而是按"编辑行为 + 兼容阶段"设计：默认 LWW（离线优先），客户端可传 `expected_version` 切换为原子 CAS。

## 1. 需要 App 团队提供的脱敏样例

| # | 项 | 说明 |
|---|---|---|
| 1 | **创建请求样例**（`POST /api/sync/records`，`action=add`） | 完整 JSON（可脱敏数据值），用于确认：是否用 `result_data` 嵌套形态、是否携带 `record_code` |
| 2 | **更新请求样例**（`action=update`） | 关键：`data` 里是**整条记录**还是**只带变更字段**；是否同时带 `sample_info` |
| 3 | **批量请求样例**（`POST /api/sync/batch`） | `operations[]` 结构与 `syncId` 的生成规则 |
| 4 | **离线队列格式与重试策略** | 队列项字段、最大重试次数、退避规则、失败项如何保留 |
| 5 | **基准版本如何保存** | 是否保存并回传 `version`（记录级）/ `expected_version` |
| 6 | **同一记录连续离线修改** | 是"串行提交"还是"合并为最新一条"；若不串行，是否会互相覆盖 |
| 7 | **收到 409 时的行为** | 是否保留本地编辑、是否提示用户、是否自动重取后再提交 |
| 8 | **批量 `errors[]` 的处理** | 是否按 `syncId` 逐项重试；是否会整批重发（可能重复创建） |
| 9 | **是否存在"去掉版本号后重试"的逻辑** | 若有，会绕过 CAS（需明确是否接受） |

## 2. 平台侧现行契约（供 App 对照）

| 项 | 行为 |
|---|---|
| 更新语义 | **局部更新默认 merge**（未提交的业务键保留）；显式 `null` 键＝删除该键；要整体替换传 `result_data_mode:'replace'` |
| 只提交上下文 | `result_data:{canteen:'B'}` → `sample_info.canteen` 更新，**result_data 保持原值**（不会清空） |
| 扁平业务字段 | `data:{id, result:'合格'}`（无 `result_data`）→ 作为业务字段**合并**写入（兼容旧 App） |
| 上下文三键 | `testDate`/`canteen`/`inspector` **不可清空**（`null`/空串/缺省＝未提交） |
| 版本 | 带 `expected_version`（或 `version`）→ 原子 CAS：冲突 `409 VERSION_CONFLICT`；不带 → LWW 但 `version` **原子 +1** |
| 幂等 | `action=add` 以 `record_code` 唯一约束；命中且**有权**修改 → 幂等返回；命中他人记录 → `409 RECORD_CODE_CONFLICT`（不回显他人记录） |
| 批量 | 逐条独立，部分成功（`results[]`/`errors[]` 按 `syncId` 对应），不整批回滚 |
| 删除 | `action=delete`（需权限）；批量删除同样逐条 |

## 3. 建议的验收动作（App 侧）

1. 用样例 1–3 在隔离环境回放，断言响应与本地模型的映射正确（尤其 `version` 回写）。
2. 模拟两设备并发：同一记录 `version=3`，A 先成功、B 携旧版本 → 必须收到 409 且**不覆盖**。
3. 断网重试：队列项重试后不得重复创建（`record_code` 幂等）或重复追加复检。
4. 冲突后行为：B 收到 409 → 应重取最新记录并提示用户，而不是静默丢弃本地编辑。
5. 若决定启用 CAS：把 `expected_version` 纳入队列项，并定义"冲突时保留本地编辑"的交互。

## 4. 平台侧待办（依赖 App 团队回答）

- 若 App 无法串行提交同一记录：需要平台侧提供"服务端合并策略"或"冲突留痕"，否则存在覆盖风险（目前是 LWW）。
- 若 App 存在"去掉版本号重试"：需要明确这是否可接受（等价于放弃 CAS）。
