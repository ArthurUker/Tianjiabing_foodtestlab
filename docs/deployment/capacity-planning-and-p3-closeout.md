# 部署容量规划 + P3 级收尾项处理结论（窗口 C）

> 日期：2026-07-30 ｜ 范围：`sync-tenant-schemas.mjs` 容量基准测算、C-1/C-2/C-3 三个 P3 收尾项

---

## 第一部分：部署容量基准测算（租户 schema 同步）

### 1. 当前租户规模

读取 `public."School"`：**4 个租户**（demo, school-gtest, sysdynit, tianjiabing）。

> **局限性声明**：本数据来自本地开发/测试环境（macOS 开发机 + 本地 PostgreSQL），
> 不能反映真实生产规模与生产服务器（腾讯云 CVM，规格更低）的实际性能。
> 生产实测数据将由 `deploy.sh` 新增的耗时日志（见 §4）持续采集。

### 2. 单租户同步耗时实测

方法：对 4 个已存在租户逐个调用 `provisionSchool`（即 `sync-tenant-schemas.mjs` 的核心步骤，
幂等 `npx prisma db push --skip-generate`，本次为无 schema 差异的典型重部署场景）并计时：

| 租户 | 耗时 |
|---|---|
| demo | 624 ms |
| school-gtest | 501 ms |
| sysdynit | 477 ms |
| tianjiabing | 468 ms |
| **合计（4 租户）** | **2 072 ms** |

- **单租户平均 ≈ 0.5 s**（本地）；完整脚本 `SKIP_PRISMA_GENERATE=1 node sync-tenant-schemas.mjs`
  端到端实测约 2.3 s（含读 School 表 + SchoolCustomization 跨 schema 回填）。
- 耗时构成：每租户 spawn 一个 `npx prisma` 子进程（进程/引擎启动为主要开销），
  db push 本身在"无差异"时只做 introspect + diff。**有实际列变更时单租户耗时会上升**，
  经验值约 1–3 s/租户。
- 生产 CVM（低配、云盘）保守按 **本地的 3–6 倍** 估算：**单租户 1.5–3 s**。

### 3. 增长预测（线性外推，顺序执行）

同步为严格顺序 for 循环，总耗时 ≈ N × 单租户耗时，线性假设成立。
按生产保守值 3 s/租户（含变更场景余量）外推：

| 租户数 | 倍数 | 预计同步总耗时（生产保守值） |
|---|---|---|
| 4（当前） | 1× | ~12 s |
| 8 | 2× | ~24 s |
| 20 | 5× | ~60 s |
| 40 | 10× | ~2 分钟 |
| 200 | 50× | ~10 分钟（阈值线） |

**结论：以 10 分钟部署窗口为可接受阈值，顺序同步可支撑约 200 个租户。**
本系统为学校级租户（一校一租户），可预见的业务规模（数十校）距离阈值有约一个数量级的余量。
**近期（租户数 < 100）无需优化，维持现状**；仅需通过部署日志持续监控，
当单次同步耗时逼近 5 分钟（≈100 租户）时再启动下述优化。

> ⚠️ **置信度说明（第七轮收尾补充）**：上述"200 租户 / 10 分钟"阈值**不是经过充分验证的
> 工程结论**，读者不应赋予其超出实际依据的权威性：
>
> 1. **极小样本 + 单次测量**：该数字基于当前仅 4 个租户的**一次**实测（2.07 s）线性外推
>    得出，不构成严格意义上的性能测试结果（无多轮取样、无置信区间、无生产环境复测）。
> 2. **线性假设本身未经多点验证**：实际耗时还可能受网络延迟、数据库负载、连接池竞争、
>    单租户 schema 复杂度差异（表数量/索引随功能演进增长）等因素影响，租户数增大后
>    是否仍保持线性并无实测支撑；生产 CVM 的 3–6 倍换算系数亦为经验估计。
> 3. **重新校准要求**：当生产环境租户数量增长到**两位数以上**时，应利用 §4 的部署耗时
>    日志重新实测并校准本阈值，**不应长期依赖本次外推数字做部署决策**。

### 4. 已落地：部署耗时监控日志（deploy.sh §6.55）

`deploy/deploy.sh` 的租户同步步骤前后已增加耗时日志：记录开始/结束时间、租户数量
（从同步脚本输出 `② 同步 N 个租户` 提取）、总耗时（秒）。

- 纯日志增强：`tee` 仅旁路复制输出，`set -o pipefail`（脚本第 22 行已开启）保证
  `node` 非零退出码穿透管道、原样触发 `fail` 中止部署——**不改变原有执行逻辑与失败中止语义**。
- 每次部署输出形如：`⏱ 租户 schema 同步结束: ... | 租户数量: 4 | 总耗时: 3 秒`，
  可从部署日志直接绘制"租户数 vs 耗时"趋势。

### 5. 未来优化方向（当租户数 > 100 时启用）

**方案：受控并发同步**（`p-limit` 风格，并发度 4–8），将总耗时压为 N/并发度 × 单租户耗时。

与既有 fail-closed 语义的冲突评估及处置：

- 现状语义有两层：① **脚本级失败**（读 School 表失败、generate 失败等）→ exit 1 →
  deploy.sh `|| fail` 中止部署（旧版本继续服役）；② **单租户 push 失败**：`tenantSync.js`
  故意"记录 ❌ 后继续"（不因一个坏租户阻断其余租户的自愈），最终 exit 0。
- 并发化只改变执行顺序，**不需要回滚**：`db push` 每租户各自幂等，成功租户的 schema
  推进不依赖其他租户，失败租户可重跑 `npm run db:sync` 补齐——这与顺序执行时的语义完全一致。
- 但并发化时建议同步做一个收紧（顺序版同样适用）：**汇总失败租户列表，若非空则 exit 1**，
  让 deploy.sh 的 `|| fail` 生效。理由：部署场景下"带着未同步租户重启新代码"正是 P2022
  风险本身，②的宽容语义只适合启动期非阻塞自愈，不适合部署期。该收紧属行为变更，
  留待并发化改造时一并处理（当前不改，遵守本窗口授权范围）。

## 第二部分：P3 级收尾项处理结论

### C-1：refresh token 刷新缺少 userId↔schema 绑定校验 —— ✅ 已闭环（校验已存在 + 本次补齐回归测试）

**现状核实**：调研发现该项在此前 DS3-H2 修复中已实现——
`backend/routes/userRoutes.js` `/refresh-token` 第 4 步（约 224–241 行）：
以 `getUserProfile(userId)` 查得的 **DB 权威 `school_code`** 与 token 声明的 `schoolCode`
交叉比对，不一致 → 401 拒绝刷新 + `logSecurityEvent('TENANT_SCHEMA_MISMATCH', {userId, tokenSchoolCode, dbSchoolCode, ip})`。

**事件命名说明**：任务书建议命名 `TOKEN_SCHOOL_MISMATCH`；既有实现已使用
`TENANT_SCHEMA_MISMATCH` 且该事件码已进入窗口 A 的 `SECURITY:*` 告警扫描通道
（`securityAlerts.js` 按前缀捕获全部事件码）与既有文档。**保留既有命名**，避免无收益的
跨窗口改名（两者语义等价，此处备案映射关系）。

**本次补齐（缺口是回归测试）**：`tests/refreshConcurrencyBackend.test.js` 新增
describe「窗口C · C-1 · refresh token userId↔schema 绑定校验回归」：

1. 构造 schoolCode 声明被篡改为 `evil-school`（DB 权威值为 `null`）的合法签名 refresh token
   → 断言 401、不签发新令牌、`SystemLog` 落 `SECURITY:TENANT_SCHEMA_MISMATCH`；
2. 对照组：声明与 DB 一致 → 200 正常刷新，无误报。

**测试证据**：6/6 通过（本文件），全量 `npx jest --runInBand` 145/145 通过，无回归。

### C-2：校徽外链可用于访客探测/追踪 —— 结论：已知且可接受，不强行修复（已有 opt-in 收紧开关）

**评估依据**（`backend/lib/securityGuards.js` `isSafeLogoUrl`，DS3-M4/M5）：

1. **非 SSRF**：后端从不出站抓取该 URL（DS-09 核查结论），仅由登录页 `<img>` 客户端加载，
   风险上限是"学校管理员配置的外链服务器能看到访客 IP/UA"——属低危隐私探针，且配置权
   仅在学校管理员（受审计的特权角色）手中，不是匿名注入面。
2. **业务必要性**：产品明确支持两种来源——base64 上传（已有 MIME 前缀 + 魔数双重校验、
   1MB 限长、禁 SVG）与任意 http(s) 外链（学校直接引用官网 logo 的真实诉求，
   登录样式模块提供"上传/粘贴 URL"两条路径）。无法预枚举各学校官网/图床域名，
   全局硬编码白名单会破坏既有租户配置。
3. **收紧手段已存在**：`LOGO_ALLOWED_HOSTS=cdn.example.com,...` 环境变量可按部署强制
   域名白名单（含子域）；未配置时向后兼容放行，该限制已在代码注释（securityGuards.js
   98–102 行）中记录。

**结论**：维持现状。风险登记为"已知且可接受"；对隐私要求高的部署（如教育局统一部署），
运维通过配置 `LOGO_ALLOWED_HOSTS` 收紧即可，无需代码变更。

### C-3：敏感操作缺少二次密码确认（Step-up Auth）—— 结论：暂不实现

**成本评估**：非低成本。最小方案（"重输密码换短时效 step-up 令牌 + 敏感端点校验请求头"）
涉及：新端点（含防爆破限速）、令牌签发/校验/一次性语义、3 个后端端点改造、前端
角色变更/禁用/删除三处交互流程插入密码弹窗、以及配套测试——横跨窗口 A（令牌体系）
与窗口 2（用户管理端点）正在维护的代码，改动面与协调成本均不小。

**边际收益评估**：Step-up Auth 防御的核心场景是"管理员会话被劫持后执行高危操作"。
该场景在本系统已被多层纵深防御覆盖：

- access token TTL 已缩短至 30 分钟（DS3-H1），会话劫持窗口有限；
- 每请求 DB 状态回查（fail-closed）+ jti/user_all 吊销机制，被盗会话可立即作废；
- refresh token 一次性轮转 + 重放检测（触发全量吊销），令牌窃取会被主动发现；
- 全部敏感操作已有强制审计（窗口 2 统一审计规范）+ `SECURITY:*` 主动告警通道（窗口 A）；
- 最后管理员删除保护（P1-17）兜底防系统锁死。

在此基础上，二次密码确认的增量收益主要剩"防止已解锁的管理员终端被物理接触滥用"，
属低概率场景，边际收益有限。

**结论**：**暂不实现**。理由：改动横跨两个在维护窗口、成本中等偏高，而既有 30 分钟
短会话 + 状态回查 + 吊销 + 审计告警体系已覆盖其主要威胁场景，边际安全收益有限。
**建议在未来引入更细粒度权限管理（如按模块授权、审批流）时一并设计 step-up 机制**，
届时短时效提权令牌可与权限模型共用同一套基础设施，避免现在做一次性点状改造。
